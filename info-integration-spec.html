7. Webhooks & status events

EventWhenSupportedInfobip mapping
message.sent Accepted by carrier / Meta Yes DELIVERY subscription event; intermediate status group with SENT-family status name on the DLR.
message.delivered Delivered to handset Yes DELIVERY subscription event; status group DELIVERED, status name DELIVERED_TO_HANDSET.
message.read Recipient read receipt Yes SEEN subscription event in the WhatsApp events enum.
message.finalized Terminal status + final cost / billing category Partial Terminal status comes via DELIVERY with price.pricePerMessage; final billing category (WhatsApp conversation category / pricing model) is exposed via the separate BILLING event — two events, not one.
message.received (MO) Inbound from recipient Yes INBOUND_MESSAGE subscription event.
signup.state_updated WhatsApp signup IN_PROGRESS / FINISHED / FAILED   Infobip's Embedded Signup is documented as flowing the WABA registration result back into the account, but I haven't verified the specific webhook event name / payload — left blank.
template.status_updated Template APPROVED / REJECTED / PAUSED / DISABLED Yes TEMPLATE_UPDATE subscription event on the WhatsApp channel.
number.quality_updated Meta quality rating change per number   Quality rating is readable via the WhatsApp senders API, but I'm not certain whether Infobip emits a dedicated subscription event for changes — left blank.
number.tier_updated Messaging tier change (Meta limits)   Messaging tier is readable per sender, but I'm not certain whether Infobip pushes a webhook on tier change — left blank.

RequirementSupportedInfobip mapping
One webhook URL per event family, configurable on Infobip side Yes Subscriptions API: one profile.webhook.notifyUrl per subscription, scoped to an events[] array (DELIVERY, INBOUND_MESSAGE, SEEN, CLICK, TEMPLATE_UPDATE, BILLING…).
Customer scope, use-case scope, campaign ref + correlation tokens echoed on every event Yes Verified end-to-end (2026-05-11): DLR carries platform.entityId, platform.applicationId, campaignReferenceId, plus free-form callbackData.
Signed payloads (HMAC or equivalent) + key rotation   I don't want to assert this without checking the current Subscriptions/webhook signing docs — left blank.

Pull-based fallback (reports / MDR endpoint) Yes GET /messages-api/1/reports?bulkId=… drains delivery reports independently of the webhook channel.

10. Capability checklist & open questions

#CapabilitySupportedInfobip mapping
1 Programmatic creation of a customer-level scope (sub-account / entity / label) Yes Entity in the Resource Management API — created once per Hermes customer; wire field is entityName.
2 Use-case-level grouping orthogonal to customer scope Yes Application in the Resource Management API — orthogonal axis to Entity; wire field is applicationName.
3 Idempotent / GET-or-create provisioning calls No POST Application / POST Entity are not idempotent on Hermes-supplied keys; safe creation requires list-then-create against the { results, paging } list shape.
4 Customer-owned MSISDN supported (no procurement from Infobip's inventory) Yes Embedded Signup binds a customer-owned MSISDN to a WABA inside Infobip; no number lease required.
5 Meta-Embedded-Signup-based onboarding launchable from Vocalcom's own Meta App, using Infobip's solution / configuration identifier Yes Infobip publishes a configuration ID passed to FB.login; signups launched from Vocalcom's App ID under that configuration land in our Infobip account.
6 Server-side API to hand off the captured WABA after signup completes Yes Infobip exposes a server-side WABA / sender registration endpoint after Embedded Signup returns wabaId + phoneNumberId.
7 Automatic number ↔ customer-scope binding on Infobip side Yes Resource Association API binds the registered sender to the customer's Entity (and the use-case Application).
8 Webhook for signup registration status   See note on signup.state_updated in §7 — left blank pending verification.
9 Number migration from another provider Yes Embedded Signup supports the standard Meta migration flow (two-step verification PIN); Infobip surfaces the migration outcome via the signup result.
10 Template CRUD + status read-back Yes WhatsApp templates v2 — POST /whatsapp/2/senders/{sender}/templates, GET for list/status, and PUT /whatsapp/2/senders/{sender}/templates/{name} for edits (Meta added template edit in 2023; Infobip exposes it).
11 Webhook for template status changes Yes TEMPLATE_UPDATE subscription event.
12 Single send endpoint covering text / media / template / interactive Yes Unified POST /messages-api/1/messages — one endpoint, content.body.type discriminates text / image / document / etc., template as a peer for template sends.
13 Client-supplied message ID or stable echo-back field Yes Both — client-supplied messageId per recipient, plus callbackData as a free-form echo-back field.
14 Bulk send with per-recipient IDs Yes Single POST returns a bulkId and a per-recipient messageId; both appear on every subsequent DLR.
15 Use-case scope / customer scope / campaign reference echoed on every event Yes Verified end-to-end: platform.entityId, platform.applicationId, campaignReferenceId all round-trip on the DLR.
16 DLR webhook with status + error + cost Yes DELIVERY webhook carries status group / name, error code + permanent flag, and price.pricePerMessage / currency.
17 Inbound MO webhook with correlation token Yes INBOUND_MESSAGE webhook returns the original send's correlation token so MOs match back to the outbound thread.
18 Pull-based reports endpoint for missed webhooks Yes GET /messages-api/1/reports?bulkId=….
19 Signed webhook payloads + documented retry policy   Not asserting without verifying the current published behaviour — left blank.
20 Per-customer billing breakdown in usage reports Yes Analytics + Exports APIs support entityId as a dimension; per-send price already arrives on the DLR.
21 Per-number / per-campaign breakdown in usage reports Yes Sender (MSISDN) and campaignReferenceId are both available dimensions on the Analytics / Exports APIs.
22 Monthly invoice-grade export   Infobip issues monthly invoices via its commercial channel, but I don't want to assert the exact invoice-export API shape without verifying — left blank.
23 Channel failover (WhatsApp → SMS) in one send call Yes Unified Messages API supports multi-channel messages with a configured failover order on the same request.
24 Quality rating & messaging tier visible per number Yes Both fields are exposed per sender via the WhatsApp senders API (read side); see §7 for the open question on change webhooks.

Cells marked blank are intentionally unfilled rather than guessed: they correspond to capabilities for which I don't have a confidently verified Infobip-side mapping. They should be confirmed against the live Infobip docs / a probe against xr5e2e.api.infobip.com before being asserted in the master spec.
