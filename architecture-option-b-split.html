Option B — Admin + HermesWebHooks split

Provisioning in Admin (net472), runtime in HermesWebHooks (net8.0), bridged by a .NET Standard 2.0 shared library in Library/Infobip.Integration.Shared.

Verdict. Split along the existing management-plane / data-plane fault line. Admin owns provisioning (what it's already for); HermesWebHooks owns runtime (where the legacy InfoBip plugin already does the same job). The shared library targets netstandard2.0 so net472 and net8.0 reference one assembly — no HermesWebHooks port required.

Constraints on the shared library

  • Pin Microsoft.Extensions.* to ≤ 5.0.x (newer drops netstandard2.0).
  • Newtonsoft.Json, not System.Text.Json. Polly v7, not v8.
  • No IAsyncEnumerable, no nullable reference types on the public API.
  • EF Core stays out of the shared library — persistence is HermesWebHooks-local, not a shared contract.
  • Consumed as a direct project reference (<ProjectReference>) — no NuGet packaging.

Roadmap

P0
Commit. netstandard2.0 shared lib; provisioning in Admin; runtime in HermesWebHooks (stays on net8.0).
P1
Stand up Library/Infobip.Integration.Shared. Port client + DTOs from HermesMessaging. Lives in the repo and is consumed as a project reference by both Admin and HermesWebHooks.
P2
Provisioning controllers in Admin (WebAPI 2). Persist mappings in config DB. Wire WebAdmin UI panels.
P3
Runtime controllers in HermesWebHooks — Speed2LeadMessagesController, WebhooksController. Add <ProjectReference> to the shared library.
P4
EF Core 8 dispatch table in HermesWebHooks. Migrations checked in.
P5
IInboundForwarder wiring — REST / DB / fan-out implementation matching the deployment's downstream consumer.
P6
Sunset legacy InfoBip plugin after parity on xr5e2e.
