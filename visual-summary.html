4. Setup Flow — Application & Entity Creation

Provisioning is self-healing on service startup: every time HermesMessaging.ApiService boots, it runs a hosted reconciliation job that ensures (a) every Hermes use case has its Infobip Application, and (b) every Hermes Customer has its Infobip Entity. After startup, new customers get their Entity created eagerly at customer creation time. Nothing is "installed" — operators never have to run a bootstrap command.

4.2 Entity reconciliation on startup + eager creation thereafter

Same hosted-service pattern, two phases. On boot, the reconciler scans the Hermes Customer table and creates an Entity for any customer that doesn't yet have one in InfobipCustomerMapping in provisioned state. After startup, the normal customer-creation path creates the Entity inline — the reconciler exists to heal drift, not to be the primary path.

Decouples identity from product.
Order on boot: §4.1 (Applications) runs before §4.2 (Entities) — an Entity may reference an Application context for downstream binding, and Resource Associations require both. The hosted service is ordered explicitly via DI registration.
Drift recovery: if Infobip drops an Application or Entity (e.g. manual cleanup, account migration), the next service restart re-creates it; no manual intervention.
Order matters at send time: the Application must exist before any outbound send tags applicationId; the Entity must exist before any send tags entityId or any number is associated to that customer.

5. Number Enrollment — Bringing the Customer's MSISDN via Meta Embedded Signup

With the Application (§4.1) and Entity (§4.2) in place, the next prerequisite before any send is a sender number. Hermes does not lease numbers from Infobip's pool — the customer brings their own MSISDN. For WhatsApp specifically, Hermes onboards each tenant's number through Meta's Embedded Signup (ES) flow, accessed via Infobip's Tech Provider Program (TPP). Hermes registers as a Tech Provider with Meta, hosts its own ES UI (using Meta's Facebook JS SDK), launches ES against Infobip's solutionId, and after the tenant completes ES, Hermes hands the captured wabaId off to Infobip via POST /whatsapp/1/embedded-signup/registrations/share-waba. Under TPP, Infobip's "Automatic Resource Association" feature auto-creates the matching entityId for the tenant's Business Manager ID during ES, so Hermes never drives Resource Association explicitly for WhatsApp.

The webhook URL is given to Infobip's account manager.

6. Resources vs Subscriptions — Complementary, Not Alternative

Before we look at the send pipeline, it is worth pausing on a distinction that is easy to confuse: Resource vs Subscription. Everything we just built in §4 and §5 (Application, Entity, Number) lives in the Resource layer — assets that exist in the Infobip account. A Subscription is a different object entirely: a routing rule for inbound events. The two are complementary, not alternatives, and the distinction maps directly to the direction of traffic:

Outbound (MT) only needs Resources. Inbound (MO) needs Resources plus a Subscription per channel. Because the current phase is outbound-only, the entire §7 / §8 send pipeline below works on Resources alone — no Subscription object needs to exist.

6.1 What this means for the current phase (outbound-only)

Subscriptions are NOT required to send. The outbound pipeline in §7 / §8 only needs the Resource layer in place: an Application (§4.1), an Entity (§4.2), and a sender number (§5). Delivery reports come back through the per-send notifyUrl on each message — no pre-created subscription object needed for the verified outbound roundtrip.

Subscriptions become mandatory in Phase 3 (inbound + webhooks). They are configured per channel: one SMS-MO subscription and one WhatsApp-MO subscription on the same number are two independent objects.

10. Proposed MSSQL Tables

All passthrough today — no DB persistence in Hermes. Existing Customer table stays untouched. Infobip connection settings (BaseUrl, ApiKey) stay in appsettings.json — moving them to the DB would require runtime decryption on every send, with no upside given a single per-deployment key. The InfobipConfiguration table below stores only observed/derived state (health-check results, fingerprints, sync metadata), never the secret itself.

Naming convention: every Infobip-related table uses the Infobip prefix (PascalCase in SQL/EF, INFOBIP_ in the ER diagram below). This keeps the integration layer cleanly grouped and easy to grep.

Persists the response metadata returned by POST /messages-api/1/messages — never the message body — so DLRs (push or pull), status refresh, error recovery, and retries have a durable handle. Provisioning state values (in InfobipCustomerMapping.ProvisioningState): pending → provisioning → provisioned → failed

Registration state values (in InfobipPhoneNumber.RegistrationState): requested → procuring → pending_registration → pending_approval → active → suspended / decommissioned

Dispatch status values (in InfobipMessageDispatch.LatestStatusGroupName): PENDING → DELIVERED · UNDELIVERABLE · EXPIRED · REJECTED (terminal groups set FinalizedAt; DELIVERED additionally sets DeliveredAt).

Dispatch write path: (1) on send response — one row per MessageAck in the SendMessagesResponse body (initial group is usually PENDING); (2) on DLR push via Subscriptions webhook — match by MessageId, update LatestStatus* / LatestError*, bump LastStatusRefreshAt; (3) on DLR pull via GET /messages-api/1/reports — same shape, used to recover from missed webhooks; (4) refresh worker drains PENDING rows older than the refresh window; (5) retry for non-permanent errors creates a new row with a new MessageId and RetryOfMessageId pointing back, leaving the prior row as the audit trail.

Body NOT stored. No Text, Template, Variables, MediaUrl. Reasons: GDPR data-minimisation (bodies are typically customer PII) and storage growth at send volume. CorrelationData + CallbackData are kept because they are the only durable Hermes-side handles for matching a stray DLR / MO back to a ContactAttempt.

Health status values (in InfobipConfiguration.HealthStatus): Healthy (last probe < interval & HTTP 2xx) → Degraded (1–2 consecutive failures or latency > threshold) → Unhealthy (≥ 3 consecutive failures) → Unknown (never probed since boot).

Health-check writer: a lightweight background job (default every 60 s) issues a benign read against the configured Infobip account (TBD — generic Infobip health endpoint, e.g. GET /account/1/account) and updates the singleton row. The same row is read by the admin UI in §16 and exposed on /health/ready for orchestrators.

15.1 Numbers as first-class entities — not campaign-scoped

Proposal: a number lives in its own registry table, independent of any campaign. Its approval/registration status is tracked there and kept fresh by an async worker that polls the provider. A campaign can only pick from numbers whose status is Approved. Today the design treats numbers as passthrough; this point pushes the model toward "number is a long-lived asset, campaign just references it."

15.2 Provider abstraction — Infobip-replaceable from day one

Proposal: design the layer generically so swapping Infobip for Twilio (or adding a second provider) is a config change, not a rewrite. One IMessagingProvider contract; one worker per provider implementation. Each worker exposes a health endpoint (alive / API key valid / last-success timestamp) and runs independently from the send path — it can keep syncing number statuses even if no sends are flowing.

15.3 Multi-channel per number — each number can serve many channels

Proposal: the same MSISDN can be enrolled on several channels (WhatsApp, SMS, RCS, Voice), and each channel can be served by a different provider. Under a number in the admin UI, a dropdown lists the channels it's enrolled on. Each (number × channel) row points to the provider responsible for it; the corresponding provider's worker is what keeps that row's status fresh.

15.4 Campaign creation — channel-first, and the provider question

Proposal: the campaign builder starts with the channel. Once a channel is picked, the number dropdown is filtered to numbers that have an Approved binding for that channel.
