Option A — Single host (HermesWebHooks net8.0)

New Infobip integration lives in HermesWebHooks as sibling controllers — not as plugins. No new deployable.

Verdict. Admin is .NET Framework 4.8 and cannot host modern typed-HttpClient ASP.NET Core code. HermesWebHooks is the only viable host inside the existing repo. Add new controllers next to PluginsController/VMSController; downgrade new code from net10 → net8; keep legacy InfoBip plugin (ccaas/1) running side-by-side until P5 sunset.

Key constraints

  • Sibling controllers, not IProviderPlugin implementations — no plugin-contract drag.
  • New code downgrades net10 → net8.0 (no breaking APIs used; drop Aspire).
  • Two HTTP libraries coexist in-process: RestSharp (legacy plugins) + typed HttpClient (new code).
  • Disambiguate inbound: legacy plugin handles campaign-keyed traffic; new controller handles applicationId/entityId-keyed traffic.
  • Do not reuse REDISLayer KV for the dispatch table — needs indexed lookups and atomic status updates.
  • Do not put new code in Admin/Web_Service — net48 cannot host the modern stack.

Roadmap

P0
Commit. New Infobip.Integration library + Infobip controllers folder in HermesWebHooksApp. Document decision.
P1
Port client + DTOs net10 → net8. Drop Aspire. Keep typed HttpClient, IOptions, System.Text.Json.
P2
Wire provisioning + outbound controllers into HermesWebHooksApp. Add "Infobip" appsettings section.
P3
WebhooksController + EF Core 8 dispatch table. Idempotent on messageId. Return 200 on parse so Infobip stops retrying.
P4
IInboundForwarder wiring to the configured downstream consumer (REST / DB / fan-out).
P5
Sunset legacy InfoBip plugin. Migrate tenants from ccaas/1/sms/2 to messages-api/1; remove after one fallback release.
